# 面试讲述提纲

按源码主线复习、典型追问和动手测试，可配合阅读 [2-1 面试核心复习地图](interview-review-guide.md)。

## 三分钟版本

项目背景：公司的自动化测试平台由 Python Web 接收用户操作，再批量创建执行记录并向 RabbitMQ 下发用例。用例规模上来后，Python 进程既要承担 Web 流量，又要一次性加载用例；Pika `BlockingConnection` 需要加全局锁，发布阶段基本串行，导致大版本下发慢并占用 Web 工作进程。

我的方案：没有重写整个 Python 服务，而是识别出“用例下发”这个边界，把查询、批量落库和 MQ 发布抽成独立 Go gRPC 引擎。Python Web 仍负责业务入口和最终状态，执行机仍回调 Python Web，因此迁移面比较小。Go 端采用游标分片、固定工作协程和 AMQP channel 池并行发布，通过服务端流返回分片进度，并用全局并发上限做过载保护。

最难的问题：MySQL 与 RabbitMQ 无法原子提交。如果数据库成功后进程在发布前崩溃，任务会永久丢失；如果消息确认后状态回写失败，又可能重复发布。我采用事务 Outbox 和至少一次投递，执行记录与消息同事务写入，Relay 用租约、随机令牌和 `SKIP LOCKED` 支持多实例恢复；消息以 `execution_id` 去重。同时使用 Publisher Confirm 和 `mandatory` 区分 Broker 接收与真实可路由，批量异常时保留已经确认的部分成功结果。

结果：线上已经完成的是从 Python Web 抽离 Go 下发引擎以及批量并发优化；可靠性、幂等、故障恢复和完整测试是我在复盘后继续完成并在本地中间件验证的演进版本。性能数据只报实际压测结果，并说明机器、用例量、并发参数和成功率。

## 面试官可能追问

### 为什么不是 Python 多进程或异步库

可以优化，但 Python Web 仍会同时承担长任务和在线请求，故障域、资源隔离和发布节奏难独立控制。下发是边界稳定、数据密集且并发模型清晰的能力，拆服务后可以独立扩缩容。代价是多了一次 RPC 和部署复杂度，所以只抽热点，不迁移最终状态等业务逻辑。

### 为什么不用一个数据库事务包住 MQ 发布

数据库事务无法回滚已经发送到 RabbitMQ 的消息，长事务还会占用连接和锁。正确做法是承认两个系统没有共同事务，通过 Outbox 把“待发送事实”与业务记录原子落库，再用至少一次投递和消费端幂等收敛。

### Publisher Confirm 为什么还要 mandatory

Confirm 的 ack 只说明交换机接收消息。如果路由键没有任何绑定，消息仍可能被丢弃。`mandatory=true` 会收到 `basic.return`，引擎才能把 NO_ROUTE 识别为下发失败。

### 为什么 Outbox 需要租约令牌

租约过期只能允许别人接管，不能阻止旧实例恢复后迟到回写。每次领取生成新令牌，状态更新同时匹配令牌，旧实例的更新影响零行并失败，避免覆盖新持有者结果。

### 如何处理客户端超时或断开

未发布部分随请求上下文取消，停止继续扫描和发布；已经完成 MQ 发布的分片必须用独立的短超时上下文完成状态补偿，否则消息已入队但 Outbox 可能长期停在 PENDING。请求重试复用 `request_id`，数据库唯一键避免重复建单。

### 这是 exactly-once 吗

不是。MQ 已确认、数据库回写前崩溃时无法可靠判断消息是否已经到达，因此系统明确提供 at-least-once。执行机必须按 `execution_id` 去重。能明确说出不能做到什么，比笼统声称“消息绝不重复”更可信。

## 讲述红线

- 可以说“这是我实现并本地验证的版本”，不要把未上线能力说成已承受线上流量。
- 只使用真实性能数据；没有原始日志时保留结果模板，不现场编数字。
- 不把下发状态 WAIT 当作最终执行成功；最终 SUCCESS/FAILED 仍由执行机回调 Python Web。
- 主动说明至少一次语义和消费端去重要求，不宣称绝对不丢不重。
